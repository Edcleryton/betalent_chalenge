# UI Test Plan - Sauce Demo

## 1. Overview
This document describes the test strategy, covered scenarios, and automation results for the user interface of the Sauce Demo platform.

## 2. Strategy and Prioritization

### 2.1 Approach: Risk-Based Testing

Flows were selected and prioritized based on **user risk** — combining business impact (what the failure prevents the user from doing) with failure probability (where SPA applications often present defects).

The execution order is not arbitrary: each group depends on the previous one to function.

| Priority | Flow | Risk Justification |
|---|---|---|
| 1 | Authentication (Login/Logout) | Blocker: without login, no other flow works |
| 2 | Product Listing and Sorting | Entry point of the purchase journey; broken sorting prevents price comparison |
| 3 | Cart (add/remove) | Core of conversion; incorrect badge generates user distrust |
| 4 | Full Checkout | Highest business impact: failure here = lost sale |
| 5 | Form validation | Prevents orders with invalid data; lack of validation = corrupted data |
| 6 | Page navigation | Continuity flow; broken links interrupt the journey |
| 7 | Accessibility (WCAG) | Legal and inclusion risk; soft assertion for monitoring without blocking CI |
| 8 | Tests by user persona | Verifies that known bugs are documented and tracked per profile |

### 2.2 User Selection Criteria

SauceDemo provides 6 test personas, each simulating a different class of risk:

| User | Risk Class | What it validates |
|---|---|---|
| `standard_user` | Baseline / happy path | Reference: if it fails, the application is down for everyone |
| `locked_out_user` | Authentication boundary | Correct blocking with appropriate message — covered in `auth.setup.ts` |
| `problem_user` | Functional bugs | Incorrect images, broken cart, silent sort — defects that go unnoticed in the happy path |
| `performance_glitch_user` | Performance degradation | Validates that the application is usable even under slowness; requires explicit timeout tolerance |
| `error_user` | Error state resilience | More severe bugs: checkout does not complete even with valid data (prevents sale) |
| `visual_user` | Visual regression and layout | 404 images, buttons out of viewport, broken alignments — a class of defect invisible in functional tests |

**Why 5 profiles instead of just `standard_user`?** Each persona exposes a class of defect that does not appear in the happy path. Testing only `standard_user` would give a false sense of quality — `error_user` and `visual_user` bugs are in production and affect real users.

**Why is `locked_out_user` not in `saucedemo-users.spec.ts`?** Because its only testable behavior is the error message on login — already covered in `auth.setup.ts`. It makes no sense to build a full flow suite for a user who never gets past the login screen.

### 2.3 What was out of scope and why

| Item | Reason for exclusion |
|---|---|
| Real payment | SauceDemo has no payment gateway — checkout finishes without charging |
| Load/stress tests | Out of study scope; `performance_glitch_user` already covers behavior under simulated slowness |
| API tests directly via UI | SauceDemo uses static data; there is no real backend to intercept |
| Visual_user in mobile viewports | Visual bugs are CSS-level and manifest on desktop; mobile does not add new cases for this persona |

### 2.4 Pipeline Decision

**All 5 profiles run on each push.** Intentional decision in the context of this portfolio: to demonstrate full bug coverage at each execution. In a real production project, `error_user` and `visual_user` would be moved to a separate regression suite (trigger: PR + schedule), keeping only `standard_user` as a smoke test on push.

### 2.5 Entry and Exit Criteria (ISO/IEC/IEEE 29119-3)

**Entry Criteria — conditions to start the suite:**

| Criterion | How to verify |
|---|---|
| `.env` file present and filled | `cat .env` — all user and password variables defined |
| SauceDemo accessible | `curl -o /dev/null -s -w "%{http_code}" https://www.saucedemo.com` returns `200` |
| Playwright installed | `bunx playwright --version` returns ≥ 1.44.0 |
| Browsers installed | `bunx playwright install` executed successfully (Chromium, Chrome, WebKit) |
| StorageState generated | `playwright/.auth/user.json` exists (generated by `auth.setup.ts`) |

**Exit Criteria — conditions to end the cycle:**

| Criterion | Condition |
|---|---|
| Complete coverage | All 48 cases executed without unplanned `SKIP` |
| Registered incidents | All `FAIL` have a Bug ID with severity and traceability in `traceability.md` |
| Report available | `playwright-report/index.html` generated and accessible |

**Suspension and Resumption Criteria:**

| Suspension Condition | Resumption Criterion |
|---|---|
| SauceDemo unavailable for more than 10 minutes | Service restored + smoke test UI-01 (`standard_user` login) successful |
| Failure in `auth.setup.ts` preventing storageState generation | Dependency resolved + storageState regenerated successfully |
| CI environment without internet access | Access restored + pipeline re-triggered |

-   **Playwright (TypeScript):** Chosen for its speed, reliability, and native support for multiple browsers and devices.
-   **Page Object Model (POM):** Standardization of code structure to facilitate maintenance.
-   **@axe-core/playwright:** Used for automated accessibility scanning.

## 4. Key Differentiators (Level 2)
-   **Responsiveness:** Tests run on Desktop Viewports (Chromium), Mobile Android (Pixel 5), and Mobile iOS (iPhone 12).
-   **Accessibility:** axe-core scan on 3 distinct pages: Login (UI-18), Inventory (UI-07/08), and Cart (UI-19).
-   **POM:** Modularized structure with `LoginPage`, `ProductsPage`, `CheckoutPage`, and `CartPage`.
-   **Multiple users:** All 6 types covered (`standard_user`, `locked_out_user`, `problem_user`, `performance_glitch_user`, `error_user`, `visual_user`) — isolated suites per user in `saucedemo-users.spec.ts` (27 tests, total: **48 UI tests**).
-   **In-depth bug exploration:** 21 bugs confirmed in production — each test uses `expect(value, '[BUG-XX] diagnosis')` to fail with ID and traceable context directly in the Playwright report.
-   **Form validation:** Required fields covered in login (UI-14, UI-15) and checkout (UI-16).
-   **Multi-item flow:** Cart with 2 items and subtotal math verification (UI-17).

## 5. Bug Analysis & Improvement Suggestions

### Found Bugs (Accessibility):
1.  **Lack of Main Landmark:** The page does not have a `<main>` tag, making navigation by screen readers difficult.
2.  **Heading Hierarchy:** Lack of `<h1>` tag on login and inventory pages.
3.  **Contrast and Labels:** The sort selector does not have an associated accessible label.

### Found Bugs (Functional):
4.  **BUG-UI-04 — Checkout without clarity on final value:** The review screen (step 2) displays only "Item total" without including the shipping cost in the calculation, creating ambiguity about the total charged to the user.

### Improvement Suggestions:
-   Add semantic HTML5 tags (`<main>`, `<footer>`, `<header>`).
-   Improve `aria-label` attributes on add-to-cart buttons to distinguish which product is being manipulated.

## 6. Risk Analysis
-   **Flakiness:** Sauce Demo is a shared environment; network slowness can cause timeouts (mitigated with Playwright auto-waits).
-   **Static Data:** `data-test` selectors are good, but if the application changes the structure of dynamic IDs, tests may break.
